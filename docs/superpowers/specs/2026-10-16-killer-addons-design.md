# Killer Add-ons Design

**Status:** Approved architecture for implementation planning
**Date:** 2026-10-16

## 1. Goal

Let a user open a Killer’s existing Character Workspace **Power & Add-ons** route, read the verified Power name and concise summary, and record quantities for that Killer’s live Add-ons. Each Add-on has artwork, name, rarity, quantity controls, and verified description/details. This is inventory tracking, not a build planner or strategy guide.

The feature must preserve Survivor inventory, existing schema-v2 saves, unknown namespaced quantities, offline operation, and the current local-first safety model.

## 2. Existing Survivor Inventory Architecture Map

### Data sources and runtime catalog

- `data/survivor-inventory-verified.json` is the canonical research input. It has patch and verification metadata, provenance, item families, 38 Items, and 54 Add-ons. Records carry stable source identity, aliases, rarity, effects/descriptions, qualification metadata, and artwork path/hash fields.
- `data/catalog.js` exports canonical `characters` and `characterById` entries with stable IDs and roles.
- `data/inventory-catalog.js` imports the Survivor source and `adaptInventoryCatalog(source, role)` validates and adapts its records. It exports `inventoryEntities`, `inventoryEntityById`, and `inventoryCatalogStatus`. Killer Add-ons and Power status are currently unavailable; `killerPowerByCharacterId` is an empty placeholder.
- The existing Survivor adapter clones rich source rows into runtime entities. The Killer adapter should instead project the smaller runtime shape needed by the UI and asset generator, without changing Survivor behavior.

### Inventory and saves

- Schema v2 stores each character’s sparse `inventory.items` and `inventory.addons` maps.
- `src/inventory-quantities.js` defines `freshInventory`, `canonicalizeQuantityMaps`, `parseQuantityInput`, and `assertQuantityEntity`. It already recognizes `killer-addon-*` IDs in `addons`, checks known character role, and rejects a resolved Killer Add-on on a different Killer.
- Quantities must be non-negative safe integers at validation boundaries. Zero is omitted from canonical maps. Unknown correctly namespaced IDs are retained with warnings; a resolved wrong-role, wrong-map, or wrong-Killer entity is rejected.
- `src/model.js` keeps `SCHEMA_VERSION = 2`, applies v1 structural migration in `validateSave`, validates v2 through `validateCompleteV2`, and exposes `parseSave` / `exportSave`. `src/storage.js` backs up and replaces saves; imports replace rather than merge. A pre-feature v2 save already has empty per-character inventory maps and therefore loads with zero Killer quantities.

### UI and editing

- `src/character-workspace.js` already reserves the role-correct `power-addons` route for Killers.
- `src/app.js` renders the workspace through `characterWorkspaceHeader`, `characterOverview`, and `characterWorkspaceView`. Survivor inventory uses `stockView`, `stockInput`, `stepStock`, `acceptStock`, and `inventoryDetail`; the Killer route still renders an unavailable placeholder.
- `src/inventory-interaction.js` supplies shared quantity state and helpers: `createQuantityInteraction`, `updateQuantityInput`, `acceptQuantityInput`, `visibleQuantityEntries`, `regroupQuantityEntries`, `quantityFocusAfterCommit`, and `stepQuantityInput`.
- `src/character-edit.js` handles quantity edits in the explicit Edit Character draft. The Survivor Items & Add-ons workspace instead saves a valid quantity on Enter or blur, while preserving pending edits and focus through errors.
- Keep the Killer workspace on the direct-save interaction used by the Survivor inventory workspace. Reuse shared quantity helpers and writer/error behavior; do not route Killer inventory through Survivor family selection or compatibility semantics.

### Artwork, build, and release

- Current Killer Power/Add-on art is in `images/updated-images/Powers and Add-ons/`. It contains 2,167 PNG files, including Power art, alternate/background variants, and non-live folders; filenames and display names are not a safe runtime lookup key.
- Survivor inventory art is already curated under `images/survivor-items-addons/`, with explicit source record `imagePath` and `imageSha256`.
- `scripts/generate-assets.mjs` implements `generateAssetManifest`, `writeAssetManifest`, and `assertInventoryAssetPath`. It accepts only explicitly referenced files, verifies source hashes and PNG structure, and records intentional null fallbacks.
- `data/asset-manifest.json` is generated by `scripts/build.mjs` through `buildProject`; it is not hand-edited. `src/assets.js` resolves an inventory ID through `inventoryIconPath(id, manifest)`, returning a path or null fallback.
- `scripts/release.mjs` stages only paths in the generated manifest, checks hashes/dimensions, and verifies the staged runtime allowlist. The bundle embeds catalogs and the manifest; runtime does not fetch catalog JSON.
- Tests are organized around `tests/inventory-catalog.test.js`, `tests/inventory-quantities.test.js`, `tests/inventory-assets.test.js`, `tests/storage.test.js`, `tests/model.test.js`, `tests/character-workspace.test.js`, `tests/release.test.js`, `tests/asset-build.test.js`, and the Playwright regressions in `tests/browser/`. `npm run test:browser` runs the browser suite against the staged runtime using Edge by default; `--chrome` selects Chrome.

### Documentation finding

`README.md` line 145 incorrectly says exported saves are schema v1. The introduction and `docs/runtime-README.md` correctly describe schema v2. The implementation plan includes correcting that single stale export claim.

## 3. Killer-Specific Differences

- A Killer Add-on belongs to one specific Killer’s Power pool. Every source record must carry an explicit canonical `characterId`; ownership is never inferred from a display name, Power name, directory, filename, or record order.
- Killer Add-ons all occupy `inventory.addons`, but unlike Survivor Add-ons they do not attach to an Item family or compatible Item list.
- Add-on descriptions can change Power behavior in many ways, but the first version only records inventory and presents verified text. It does not calculate modified values, simulate conditions, or validate combinations.
- The current Power source is the top-level array `data/dbd-killer-power-master-44-FINAL-verified-10.2.1.json` with 44 records. Records have `killerName`, `powerName`, `researchStatus`, `shortSummary`, mechanics, and other research fields. No stable character or mechanic IDs exist in that file. Do not modify it.
- Some Add-ons may have conditional, transformational, stacking, or cross-Add-on effects. Those are factual description concerns, not inventory semantics.

## 4. Proposed Data Architecture

### Canonical research input

Use one canonical, versioned master file, provisionally `data/dbd-killer-addons-live-10.2.1.json`. Do not use the old 720-Add-on corpus as the live catalog. The exact filename and game version follow the verified dataset that is eventually supplied.

At a high level, the JSON contains:

- Catalog metadata: live patch, verification date/status, expected record count, and provenance.
- `addons[]`: one record per live Add-on with an immutable canonical `id`, explicit `characterId`, name, rarity, concise description/details, optional search aliases, per-record verification status, sources/recent changes, and artwork mapping.
- Artwork mapping: original `sourcePath` for audit, curated packaged `path`, and SHA-256. A record without art must carry an explicit fallback reason.
- Optional `powerEffects[]`: descriptive text such as a mechanic label and verified effect description. It contains no foreign key, mechanic array index, generated mechanic ID, or display-name join.

Canonical IDs should be explicit, namespaced `killer-addon-*` values, stable across display-name changes, and unique across the full catalog. A convention such as `killer-addon-{characterId}-{semanticSlug}` is suitable for assigning them, but runtime must validate the stored ID instead of generating identity from the current name.

The catalog generator validates the declared record count, unique IDs, valid Killer `characterId`, valid rarity, per-record verification status, unique/non-ambiguous aliases, and explicit artwork/fallback metadata. A canonical Add-on ID may have only one owner; duplicate IDs with different Killer owners are rejected. It rejects a record attached to a Survivor or a nonexistent character.

### Runtime projection

`scripts/generate-killer-runtime-catalog.mjs` should validate and project the rich Add-on source plus the Power source into a compact generated `data/killer-runtime-catalog.json`. That output contains only normalized Add-on entities and the Power name/summary lookup. `scripts/build.mjs` generates it before importing the asset generator and bundling. The checked-in generated file lets the normal test suite load the app catalog before a build; tests also verify it matches the canonical sources.

`data/inventory-catalog.js` retains the existing Survivor adapter and imports the compact generated Killer output. The combined `inventoryEntities` and `inventoryEntityById` remain the single authoritative runtime registry passed to save validation and inventory UI.

Each generated Killer runtime entity contains only:

`id`, `kind: 'killer-addon'`, `role: 'killer'`, `map: 'addons'`, `characterId`, `name`, `rarity`, `order`, optional `aliases`, `description`, optional descriptive `powerEffects` if displayed, and explicit `imagePath` / `imageSha256` for the established asset generator. Research sources, verification notes, archive metadata, and patch history stay out of the application bundle unless a UI later needs them.

For the Power panel, generate only `characterId`, `powerName`, and `shortSummary` into `killerPowerByCharacterId`. Since the Power JSON has no character IDs, use a reviewed explicit character-ID-to-source-record mapping and validate a one-to-one mapping of all 44 verified records. This lookup is only for displaying the Killer’s Power. Add-on ownership still comes solely from the Add-on row’s explicit `characterId`. The 714 KB research Power file is not bundled.

## 5. Power / Add-on Relationship

Do not change the Power JSON and do not establish foreign-key relationships to mechanic names, indexes, or IDs. The Power file’s mechanic names and `addonRelevantMechanics` are descriptive and may change during research updates.

For v1, optional Add-on `powerEffects` are descriptive metadata only. A useful shape is `{ mechanicDescription, effectDescription }`; both are text, not referential keys. The UI may show these details but must not join, calculate, validate, or claim that a Power mechanic record was resolved. Introduce stable mechanic IDs only after a concrete UI behavior requires them and a separate review approves that data change.

Trade-offs:

- Free text is easy to audit and resilient to absent IDs, but cannot safely drive calculators or cross-record integrity checks.
- Exact mechanic-name joins are brittle under wording changes and are explicitly out of scope.
- Generated IDs or mechanic indexes would create false stability and require changing/reprocessing the Power dataset.
- A later curated ID layer could support interactive Power explanations, at the cost of maintaining an additional reviewed relationship dataset.

## 6. Data Architecture Options

| Option | Advantages | Costs | Decision |
| --- | --- | --- | --- |
| One master verified Add-on JSON imported directly by the app adapter | One research source, cohesive audits and diffs, simple runtime lookup | Carries research/audit fields into the app bundle unless the bundler proves field-level elimination | Reject |
| 44 hand-maintained per-Killer runtime/source files | Small character-local edits | Fragmented provenance, 44-file update/audit burden, harder global duplicate/count checks | Reject |
| One master source plus a generated compact runtime JSON | One canonical research source, compact offline bundle, explicit validation boundary | Adds a generated artifact that must be regenerated and checked for staleness | **Recommend** |

## 7. Save and Inventory Model

Use the existing schema-v2 per-character `inventory.addons` map. No save-schema bump is needed.

- Missing means zero/not owned; only positive safe integer quantities are persisted.
- A quantity of zero deletes the key.
- Known Killer Add-ons must resolve to `kind: 'killer-addon'`, role `killer`, map `addons`, and the record’s exact owning `characterId`.
- Unknown valid `killer-addon-*` IDs remain preserved with the existing warning behavior.
- Resolved wrong-role or wrong-Killer records are rejected. Do not guess or silently prune them.
- Import/restore continues to replace rather than merge. No catalog change should write or normalize a save by itself.
- Schema-v1 migration remains unchanged and initializes empty maps exactly as today. Pre-feature schema-v2 saves retain their shape and display zero Killer quantities.

The catalog may make a formerly unknown imported ID resolvable. If it resolves to the wrong Killer, the existing strict ownership validation will reject that record rather than silently relocating it. Preserve the original bytes/backup and show the existing validation failure; do not introduce an automatic repair migration.

## 8. UI Model

Unlock the reserved `#character/{characterId}/power-addons` workspace route.

1. **Power:** show the selected Killer’s Power name and concise verified summary.
2. **Add-ons:** show every Add-on whose explicit `characterId` matches the selected Killer. Each card shows artwork or intentional fallback, name, rarity, current quantity, accessible increment/decrement and numeric entry controls, and verified details.
3. **Interaction:** use direct-save semantics from Survivor stock cards, shared `src/inventory-interaction.js` helpers, existing writer-lock checks, validation, save/error status, and focus recovery. Never edit another Killer’s entity.
4. **Findability:** reuse the shared name/description search, rarity filtering, and stocked-first/default catalog ordering if they remain simple in the single-Killer view. Do not add a second filtering framework.
5. **Overview:** replace the Killer “reference data unavailable” placeholder with a truthful Power/Add-ons summary and link when the catalog is ready.

The route, page heading, and shared workspace navigation already exist. Cards may reuse the existing `.stock-grid`, `.stock-card`, rarity badges, and quantity control styling. Add only the Power intro and any Killer-specific responsive details needed.

Deferred: builds/loadouts, favorites, strategy rankings, recommended combinations, synergy graphs, modified-value calculators, global Add-on encyclopedia, patch-history UI, and hard Power-mechanic linkage.

## 9. Artwork Integration

Curate selected original PNG bytes from `images/updated-images/Powers and Add-ons/` into a predictable dedicated path such as `images/killer-addons/{characterId}/{semanticSlug}.png`. Keep the raw source tree and file bytes untouched. Record original source path, curated path, and SHA-256 in the Add-on source row. Do not infer a mapping at runtime from filenames, display names, or folders.

Extend the existing inventory asset path allowlist in `scripts/generate-assets.mjs` for the curated Killer directory. `generateAssetManifest` must resolve every explicit mapping, verify the hash and PNG data, and emit a path/dimensions/hash or a declared null fallback. Keep `inventoryIconPath` generic. The normal build regenerates `data/asset-manifest.json`; release staging copies only manifest references and checks hashes/dimensions. Extend `artworkFileCheck` and browser decode coverage to include inventory assets and Killer Add-ons. No runtime network request or independent image loader is introduced.

## 10. Catalog, Build, and Release

- Generate the compact runtime JSON from the Add-on and Power sources before asset generation and bundling; import only that normalized output in the app. Do not fetch JSON in the browser or bundle the research sources.
- Keep Survivor entities and their adapter unchanged; append normalized Killer entities into the same ID map so existing quantity/save validation resolves them.
- Update `inventoryCatalogStatus.killerAddons` and `killerPowerByCharacterId` only after catalog and Power mappings validate.
- `scripts/build.mjs` remains the single build entry point and regenerates the compact Killer runtime catalog and asset manifest before bundling.
- `scripts/release.mjs` should verify Add-on catalog metadata and continue staging the exact manifest image paths. The staged artifact must include all referenced Add-on images and still contain no research-only JSON or development files.
- Update release browser coverage for Power & Add-ons, quantity persistence, image decode, and the absence of external/catalog JSON requests.

## 11. Compatibility and Validation

No schema, storage-key, character-ID, migration, backup, recovery, or import/restore format change is planned.

Validation must cover:

- Unique canonical Add-on IDs; each ID maps to exactly one explicit valid Killer owner; valid rarity; no ambiguous aliases.
- Every record verified for the catalog version; declared expected count matches records.
- Power summary mapping covers all 44 verified records exactly once without editing the Power JSON.
- Artwork is either explicit valid path/hash or an intentional fallback; all release references are staged and verified.
- Correct Killer Add-on quantities are accepted; same Add-on on another Killer is rejected.
- Unknown namespaced Killer Add-on IDs survive save/export/import round trips.
- Missing/zero quantity behavior, malformed quantities, and ownership validation remain sparse and strict.
- Existing schema-v2 saves load unchanged; Survivor item/Add-on maps are byte/value-equivalent after loading; import/export/backup/restore preserve both roles.
- Workspace route shows only the selected Killer’s Add-ons, quantity edits persist after reload, and keyboard/responsive behavior remains usable.
- Browser requests remain local; the staged file-mode runtime resolves bundled code and image references without catalog JSON requests.

## 12. Patch and Data Update Workflow

1. Research every live Add-on against the new verified source set; record version, verification status, sources, and relevant recent changes.
2. Update the single versioned master JSON and explicit stable IDs/character owners. Do not base the live list on the old 720-entry corpus.
3. Curate artwork mappings and hashes from the current raw art tree; document intentional fallbacks.
4. Run catalog and ownership validators, quantity/import-export tests, and artwork manifest/hash tests.
5. Build through `npm run build`; review generated runtime catalog, bundle, and manifest changes without hand-editing them.
6. Run `npm test`, browser regression in Edge and Chrome, and `npm run release`; inspect staged image decode and offline file check.
7. Review version/count/provenance and diff, then commit the dataset, adapters, assets, tests, and UI in focused units.

Research-only provenance belongs in the source JSON. Runtime retains only descriptions/effects that the UI displays. Release metadata can record source version and record count without bundling source citations.

## 13. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Add-on is assigned to the wrong Killer | Require explicit `characterId`; validate role and owner against canonical character IDs. |
| Display rename changes a saved ID | Freeze explicit semantic IDs; names and aliases never generate IDs at runtime. |
| Old unresolved ID becomes resolved on the wrong Killer | Keep strict rejection, preserve original export/backup, explain the conflicting ID; never auto-move it. |
| Alias collision resolves ambiguously | Validate normalized aliases globally and reject collisions before bundling. |
| Art filename or folder suggests a false mapping | Use a curated explicit record mapping and SHA-256; runtime never guesses. |
| Hash/path omitted or wrong asset changes silently | Build manifest emits only verified paths or explicit fallbacks; release checks hashes and dimensions. |
| Catalog update rewrites user data | Catalog is static; no migration or write occurs on catalog load. |
| Survivor behavior changes during shared integration | Preserve Survivor adapter and family editor; add Killer entities at the registry boundary and retain Survivor regression tests. |
| Old v1/v2 compatibility changes accidentally | Keep schema constant and migration functions untouched; run model/storage fixtures for v1 and pre-feature v2. |
| Localhost passes but file-mode release fails | Extend staged local-reference verification and `artworkFileCheck`; keep bundle self-contained. |
| Power source labels drift | Validate the explicit 44-row Power mapping as a one-to-one relation; do not use Power names to infer Add-on ownership. |

## 14. Explicitly Deferred

No loadouts/builds, favorite Add-ons, recommendations, strategy ranking, synergy calculations, modified-value calculator, global encyclopedia, patch history UI, stable Power mechanic IDs, schema change, Power JSON rewrite, Killer catalog inferred from art, or separate database/service.

## 15. Open Decisions

No architecture decision remains open. The final Add-on filename, verified patch/date, literal live record count, and row content must come from the forthcoming verified live dataset. The implementation must stop before catalog integration if that authoritative source has not been supplied or completed.

## 16. Spec Self-Review

- Scope stays on Killer Power & Add-ons workspace inventory; deferred features are explicit.
- Existing schema-v2 shape and v1 migration remain unchanged; no hidden migration or save rewrite is implied.
- Add-on ownership uses explicit `characterId`; Power summary mapping is separate and validated.
- Power mechanics are descriptive only; no index/name foreign key or Power JSON edit is proposed.
- Survivor catalog, editor, and artwork behavior remain intact; only the shared registry and asset allowlist are extended.
- Research metadata stays in the canonical input; runtime and release include only UI/build-required fields.
- Artwork paths, hashes, fallbacks, runtime lookup, browser decoding, and release staging use one existing pipeline.
